# TUNNEL security review, threat model and risk register (v3)

> **Status: internal review only. No independent audit has been performed.**
> Passing tests is not evidence of security.

Scope: `packages/core` (protocol rules), `services/engine` (the only key
holder), the web API (`app/src/app/api`), and the database schema.

## 1. Trust model

TUNNEL has no smart contract. Users trust the operator to:

* keep the server and engine running and settle every cycle;
* pay claims from the reward wallet (the operator controls its key);
* not insert fraudulent deployments (detectable, see `RANDOMNESS.md`).

Users do **not** need to trust the operator about randomness: outcomes are fixed
by a pre-committed seed plus a future blockhash and are publicly verifiable.

Users never sign a transaction and never send funds. Signing a TUNNEL message
cannot move anything from a wallet. TUNNEL never requests seed phrases or private keys.

## 2. Keys

| Key | Where | Power | Mitigation |
|---|---|---|---|
| Reward wallet | Engine only (Render secret file) | Holds the mining reserve; signs payouts | Fund only what is needed; keep the bulk of supply in the cold operator wallet; per-payout cap (`ENGINE_MAX_PAYOUT_TOKENS`); SOL fee floor; monitor balances on /admin |
| Operator wallet | Offline / hardware | Holds supply, mint authority | Revoke mint authority after launch (`create-token --revoke`) |
| Admin (password) | Anyone | `/admin`: pause, limits, RPC/mint settings | 12 h HttpOnly SameSite=Strict cookie issued after the password matches the scrypt `ADMIN_PASSWORD_HASH`; login rate limited per IP and globally; mint locked while balances exist; same-origin check; every action logged |
| `SESSION_SECRET` | Web env | Signs admin sessions | Generated by Render; 32+ bytes |

The web service holds no Solana key at all.

## 3. Review by area

### 3.1 Signed deployments (`core/deploy.ts`)
* The message must be the exact canonical rendering (parse → re-render → compare), so no extra lines or altered fields pass.
* ed25519 signature over the UTF-8 message, by the wallet named in it (tweetnacl).
* Freshness: issued ≤ 5 min ago and ≤ 30 s in the future. Replay: nonce inserted into `UsedNonce` (primary key) and signature unique on `Experiment`, inside the same transaction.
* The cycle row is locked `FOR UPDATE`; status, `closeTs` and the entropy guard are checked under the lock; close is a conditional `UPDATE` on the same row, so no deployment can commit after close.
* Energy: `energyUsed + count × cost ≤ energyPerCycle` under the lock (concurrency-tested: 8 parallel 25-energy deploys → exactly 4 succeed).
* Bounds: barrier 0–2, level 0–4, 1–100 particles, nonce charset/length, message ≤ 2 KB; DB CHECK constraints repeat them.
* Rate limits: 60/min per IP, 30/min per wallet (database-backed).

### 3.2 Settlement (`core/cycles.ts`)
* One transaction holding the cycle lock; acts only on `status = closed`; idempotent.
* Payout = nominal if Σ nominal ≤ budget, else `⌊budget · nominal / Σ nominal⌋`. Property-tested: Σ payouts ≤ budget, each ≤ nominal.
* Budget at open = `min(schedule, funded − allocated(settled) − budgets(open/closed))`. A cycle never promises tokens that were not deposited (tested).
* DB constraint `tokensAllocated ≤ emissionBudget`.

### 3.3 Claims and payouts (`core/claims.ts`, `engine/payouts.ts`)
* A claim is a signed message (same canonical/freshness/nonce rules). Positions are locked and linked to one Payout in a transaction; partial unique index `Payout_one_open_per_wallet` forbids a second open payout.
* **Exactly once:** the transfer is signed, and its signature + `lastValidBlockHeight` are stored (`requested → sending`, conditional update) *before* broadcast. A `sending` payout is re-signed only when the chain's block height has passed `lastValidBlockHeight` and `getSignatureStatuses(searchTransactionHistory)` does not know the signature. That transaction can then never land, so re-signing cannot double-pay.
* On-chain error → `failed`; positions are released back to claimable.
* Payouts wait (never fail) when the reward wallet lacks tokens or SOL, or the amount exceeds the safety cap.
* Transfers use `transferChecked` (decimals asserted) and create the recipient's ATA idempotently; the engine pays all fees. Token-2022 mints are supported (program resolved from the mint owner).

### 3.4 Secrets and data exposure
* `serverSeed` is withheld by every API until the cycle is settled or void (`publicCycle`; e2e-tested).
* Signed messages and nonces are stored for auditability; only the experiment detail endpoint returns the message.
* Errors returned to clients are fixed strings; internals are logged server-side only.

### 3.5 Abuse
* Sybil: per-wallet energy does not stop many wallets; the per-cycle emission cap bounds total extraction regardless.
* Spam: rate limits + message size limits; deployments cost the server one DB transaction.

## 4. Risk register

| Risk | Impact | Status |
|---|---|---|
| Reward wallet key compromise | Reserve stolen | Mitigated by small hot balance, cap, monitoring. Not eliminated. |
| Operator withholds settlement | Cycle voids, no rewards | Visible publicly; inherent to the server model |
| Operator inserts fake deployments | Unfair share of a cycle budget | Detectable via signatures/timestamps; inherent |
| Database loss | Owed rewards unknown | Render managed backups; restore runbook in DEPLOYMENT.md |
| RPC outage | Delayed settlement/payouts | Retries; void after 1 h; payouts wait |
| No independent audit | Unknown bugs | **Open** |
